# RingCache Architecture & Design Decisions

This document records the architectural decisions, trade-offs, alternatives considered, and unresolved questions for RingCache. All decisions are marked as **Proposed** until validated through prototypes, benchmarks, or maintainer approval.

---

## Decision Status Legend
- **Proposed**: Under evaluation; rationale documented, but awaiting validation or implementation.
- **Accepted**: Approved by project maintainers and targeted for implementation.
- **Superseded**: Replaced by a subsequent architectural decision.

---

## ADR-001: Consistent Hashing vs. Modulo Hashing

- **Status**: Accepted
- **Context**: In a distributed cache, incoming keys must be mapped efficiently to a set of $N$ storage nodes. Under traditional modulo hashing ($\text{node} = \text{hash}(\text{key}) \pmod N$), changing cluster size from $N$ to $N \pm 1$ invalidates approximately $\frac{N}{N+1}$ of all keys. In large caches, this causes massive cache misses, cascading load to backend databases, and high network congestion.
- **Decision**: Implement a consistent hash ring where keys and node identifiers map onto an identical circular token space ($[0, 2^{64}-1]$ using a deterministic 64-bit non-cryptographic hash function). Keys route to the first node with a token $\ge \text{hash}(\text{key})$ (wrapping to the lowest token at ring boundary). Implemented in `ringcache::HashRing` backed by `std::map<uint64_t, std::string>` and reader-writer synchronization (`std::shared_mutex`).
- **Alternatives Considered**:
  - *Modulo Hashing*: $O(1)$ routing calculation with zero memory overhead, but catastrophic invalidation upon node changes.
  - *Rendezvous (Highest Random Weight) Hashing*: Offers excellent redistribution properties, but key lookup requires evaluating $O(N)$ hash weights across all nodes, whereas consistent hashing can lookup in $O(\log V)$ via binary search.
  - *Range-based Partitioning*: Keys partitioned by lexicographical ranges; leads to hot spots under sequential key write workloads.
- **Trade-offs**:
  - Consistent hashing requires maintaining an ordered data structure (e.g., `std::map`) with $O(\log(N \times V))$ lookup time rather than $O(1)$ modulo arithmetic.
  - Non-uniform token distribution can cause uneven load unless mitigated by virtual nodes.
- **Validation**:
  - Validated in Milestone 2 unit tests: adding a node to a 3-node cluster remaps only $\approx 25\%$ of keys directly to the new node, leaving existing assignments undisturbed.

## ADR-002: Virtual Nodes (vnodes) for Uniform Partitioning

- **Status**: Accepted
- **Context**: With standard consistent hashing, placing a single token per physical node frequently produces unequal partition sizes on the ring, leading to severe memory imbalances and traffic hot spots.
- **Decision**: Introduce virtual nodes (vnodes). Each physical node is assigned $V$ distinct virtual tokens (default $V = 150$), generated by hashing the node identifier with an index suffix (`"{nodeId}#{index}"` for $i \in [0, V-1]$).
- **Alternatives Considered**:
  - *Single token per physical node*: Minimal memory footprint, but unacceptable variance in key allocation across small to medium clusters.
  - *Bounded-load consistent hashing*: Enforces strict load limits per node; adds dynamic coordination overhead.
  - *Capacity-weighted allocation*: Assign variable token counts proportional to machine hardware capacity.
- **Trade-offs**:
  - Vnodes provide substantially better uniformity across physical nodes and enable smoother data redistribution during node join/leave events.
  - Increases ring memory consumption ($N \times V$ entries) and makes binary search on the ring slightly slower ($O(\log(N \times V))$).
- **Validation**:
  - Validated in Milestone 2 unit tests: statistical key distribution across 3,000 keys demonstrates that $V = 150$ produces significantly lower standard deviation and balanced allocation across physical nodes compared to $V = 1$.

## ADR-003: Storage Engine and LRU Eviction Policy

- **Status**: Accepted
- **Context**: Each cache node requires an efficient in-memory storage engine that enforces a hard memory ceiling and discards entries when capacity is saturated.
- **Decision**: Implement an exact Least Recently Used (LRU) eviction engine using a hash table (`std::unordered_map`) mapping keys to iterators of a doubly-linked list (`std::list`) containing key-value pairs (`ringcache::BasicLruCache` / `ringcache::LruCache`).
  - Read/Write: Moves the accessed entry to the head of the list ($O(1)$) using `std::list::splice` without invalidating iterators.
  - Eviction: Removes entries from the tail of the list ($O(1)$) when capacity is exceeded.
  - Concurrency: Synchronized using an internal `std::mutex` ensuring thread safety across concurrent readers and writers, as read operations mutate access recency.
  - Zero Capacity: Safely defined as a no-op that rejects all insertions and returns `std::nullopt` on retrieval.
- **Alternatives Considered**:
  - *Sampled LRU (Redis approach)*: Randomly samples $K$ keys and evicts the oldest among them. Reduces memory overhead and lock contention on read paths, but provides approximate eviction.
  - *Clock / Second-Chance Eviction*: Uses a circular buffer with a reference bit.
  - *LFU (Least Frequently Used)*: Tracks frequency rather than recency; more complex to implement and susceptible to stale frequency accumulation.
- **Trade-offs**:
  - Exact LRU provides predictable, optimal recency eviction and stable $O(1)$ operations.
  - Maintaining node order requires mutating the doubly-linked list on *read* operations, requiring mutual exclusion locking across all accesses.
- **Validation**:
  - Validated in Milestone 3 unit tests: exact LRU eviction order, access recency changes, capacity 0/1 handling, empty key/value support, and high-contention multi-threaded concurrent access with zero data races.

## ADR-004: TCP Protocol and Message Framing

- **Status**: Accepted
- **Context**: Cache nodes must communicate with clients and peer nodes reliably over stream-oriented TCP. The wire protocol must be efficient, simple to parse, safe against malformed frames, and resilient to TCP segmentation and packet fragmentation.
- **Decision**: Implement a bounded newline-delimited JSON wire protocol over TCP using standalone Asio and Modern JSON (`nlohmann::json`):
  - **Frame Delimiter**: Each request and response message is encoded as a single-line UTF-8 JSON object terminated by a newline character (`\n`).
  - **Bounded Framing**: A hard limit of 64 KB (65,536 bytes) per frame is strictly enforced during stream reading and parsing. If an incoming message exceeds 64 KB before a newline delimiter is received, or if parsing fails, the connection safely rejects the frame with an error response (or drops the connection) rather than allocating unbounded memory.
  - **Request Format**:
    - `op`: Command string (`"PUT"`, `"GET"`, `"DELETE"`, `"PING"`).
    - `key`: Target cache key (string).
    - `value`: Target cache value (string, used for `"PUT"`).
    - `requestId`: Optional correlation identifier (string/integer).
  - **Response Format**:
    - `status`: Result indicator (`"OK"`, `"NOT_FOUND"`, `"ERR"`, `"PONG"`).
    - `value`: Optional returned value string (for successful `"GET"`).
    - `message`: Diagnostic error or status description.
    - `requestId`: Echoed correlation identifier.
  - **Error Handling**: Implemented using non-throwing parsing functions (`parseRequest`, `parseResponse`) that catch `nlohmann::json::parse_error` or missing required fields and return `std::nullopt` instead of leaking exceptions across the asynchronous network boundary.
- **Alternatives Considered**:
  - *Length-prefixed binary framing*: Extremely compact and eliminates delimiter scanning, but requires dedicated debugging tools and complicates inspection. Delimited JSON was adopted for Milestone 5 because it provides human-readable wire debugging while bounded parsing prevents memory exhaustion.
  - *RESP (Redis Serialization Protocol)*: Compatible with existing Redis tooling, but adds parser complexity for custom replication and routing metadata.
  - *gRPC / Protocol Buffers*: Introduces heavy external dependencies and build complexities not warranted for a lightweight C++17 cache.
- **Trade-offs**:
  - JSON encoding introduces slight serialization and deserialization overhead compared to raw binary framing.
  - Human readability, ease of testing via command-line utilities, and safe bounds provide superior developer experience and operational transparency.
- **Validation**:
  - Validated in `tests/test_protocol.cpp` and `tests/test_network_integration.cpp`: round-trip serialization and deserialization of all operations, strict rejection of frames exceeding 64 KB, handling of malformed and partial JSON payloads, empty keys/values, and network disconnects.

## ADR-005: Multi-Node Replication Strategy

- **Status**: Accepted
- **Context**: In-memory nodes may fail, experience LRU eviction pressure, or restart. To prevent total data loss and maintain cache availability, keys can be replicated across multiple nodes on the ring.
- **Decision**: Implement clockwise successor replication with a configurable replication factor $R$ managed by `ringcache::ClusterRouter`:
  - **Node Selection**: Keys route to the first node on the ring (primary) and the next $R - 1$ distinct physical nodes clockwise (replicas).
  - **Deduplication Invariant**: If active node count $N < R$, all $N$ distinct physical nodes are used. A physical node is never selected multiple times for the same key.
  - **Write Semantics**: Writes (`set`) target the primary node first. If the primary succeeds, writes propagate to all replicas. Success is declared if the primary successfully stores the value. Partial writes occur when a replica fails or has capacity 0.
  - **Read Semantics**: Primary-first read with replica fallback. If a key is missing on the primary (e.g., evicted under local memory pressure), the router falls back to replicas in clockwise order.
  - **Delete Semantics**: Deletes (`del`) target primary and all replicas, returning true if the key was deleted from at least one node.
  - **Limitations**: Best-effort/eventual consistency without distributed consensus (Raft/Paxos) or two-phase commit. Replicas manage their own local LRU eviction boundaries independently.
- **Alternatives Considered**:
  - *No Replication (Cache Only)*: Treat the cluster as an ephemeral cache where misses fall back to the underlying database. Maximizes write throughput and simplicity, but leaves backend databases vulnerable to stampedes on node loss.
  - *Quorum Consensus (Dynamo-style $W + R > N$)*: Tunable consistency, but introduces complex versioning (vector clocks) and read repair overhead.
  - *Raft / Paxos State Machine Replication*: Strong linearizability, but significantly limits write performance and adds substantial coordination overhead unsuitable for transient cache workloads.
- **Trade-offs**:
  - Successor replication provides fault tolerance against node dropouts with low coordination latency.
  - Independent LRU evictions on primary vs. replicas can cause replicas to serve slightly stale or lingering cached data after primary eviction.
- **Validation**:
  - Validated in Milestone 4 unit tests: multi-node key distribution across distinct physical nodes, replication factor boundaries ($R=1$, $R>N$, $R=0$), primary loss and replica fallback, local LRU eviction behavior across replicas, and partial write handling.

## ADR-006: Concurrency and Threading Architecture

- **Status**: Accepted
- **Context**: Cache node daemons and networked routers must handle multiple concurrent TCP connections, client requests, and replica updates without race conditions, thread starvation, or deadlock.
- **Decision**: Employ an asynchronous event-driven I/O model backed by standalone Asio with a configurable worker thread pool:
  - **Server Concurrency (`TcpServer`)**: The server runs an `asio::io_context` serviced by $T$ worker threads (configurable via `--threads`, default `std::thread::hardware_concurrency()`). Each client connection is managed by a distinct `TcpSession` using asynchronous reads and writes.
  - **Zero Lock Holding During I/O**: Network sockets are read and written asynchronously without holding any cache storage locks. Locks are only acquired during the sub-microsecond cache access within `CacheNode` / `LruCache`.
  - **Storage Synchronization**: Each node's in-memory storage is safeguarded by the internal mutex of `LruCache` (or `CacheNode`), guaranteeing serialized, thread-safe updates to the doubly-linked LRU list and hash table.
  - **Client Concurrency (`NetworkClient` & `NetworkClusterRouter`)**: `NetworkClient` provides thread-safe synchronous socket operations protected by a `std::recursive_mutex`. It utilizes non-blocking socket connect with timeout via `select()` and `SO_ERROR` verification, avoiding Windows IOCP cancellation hangs. `NetworkClusterRouter` utilizes `HashRing` reader-writer locking (`std::shared_mutex`) during key lookup and routes TCP requests to destination endpoints.
- **Alternatives Considered**:
  - *Single-Threaded Event Loop*: Minimizes synchronization, but underutilizes multi-core CPUs for concurrent JSON serialization and network parsing.
  - *Thread-Per-Connection*: Spawns a dedicated thread per connection; does not scale to thousands of concurrent idle or keepalive connections.
  - *Sharded / Partitioned Lock Striping*: Divides cache into stripes. Deferred to future optimization milestones; the current thread-safe `LruCache` mutex provides sufficient throughput with simple correctness guarantees.
- **Trade-offs**:
  - Thread pool running asynchronous Asio handlers requires careful lifetime management (`std::enable_shared_from_this`) to prevent use-after-free when sockets disconnect abruptly.
  - Decoupling network I/O from storage locking ensures maximum server responsiveness.
- **Validation**:
  - Validated in `tests/test_network_integration.cpp`: concurrent multi-process round-trips, concurrent request execution across worker threads, graceful shutdown on `SIGINT`/`SIGTERM`, and clean error propagation on peer process termination.

## ADR-007: Node Failure Detection and Ring Membership

- **Status**: Proposed
- **Context**: Nodes in a distributed cluster can crash, restart, or experience network partitions. The cluster must detect changes and update the hash ring accordingly.
- **Proposed Decision**: Adopt a two-phase evolutionary approach:
  - *Phase 1 (Initial)*: Static or coordinator-assisted configuration where cluster membership is defined via static configuration or a centralized health probe.
  - *Phase 2 (Target)*: Decentralized heartbeat / failure detector (e.g., phi-accrual or SWIM gossip protocol) to broadcast node join/leave/fail events and recompute the local ring.
- **Alternatives Considered**:
  - *Fully Centralized Coordinator (ZooKeeper / etcd / Consul)*: Simplifies consensus and membership, but introduces a heavy operational dependency.
  - *Static Configuration Only*: Simplest to test, but cannot handle dynamic cloud environments or automated failover.
- **Trade-offs**:
  - Phase 1 allows focusing first on storage and hashing correctness without building complex distributed consensus.
  - Phase 2 eliminates single points of failure but requires robust handling of split-brain scenarios and flap damping.
- **Unresolved Questions**:
  - During node departure, how are keys migrated from remaining replicas to newly assigned successors?
  - What heartbeat interval and timeout thresholds should trigger marking a node as temporarily degraded vs. dead?

## ADR-008: Testing Strategy and Fault Simulation

- **Status**: Accepted
- **Context**: Distributed caching systems suffer from subtle failure modes, including race conditions, data races, unbalanced key distributions, and partition edge cases.
- **Decision**: Implement a multi-tiered testing methodology:
  1. *Unit Testing*: Test isolated components (LRU list, hash ring token placement, protocol serialization, versioning) using deterministic unit tests.
  2. *Distribution & Statistical Verification*: Dedicated tests measuring key distribution uniformity, variance, and redistribution percentages across node additions and removals.
  3. *Concurrency & Multi-Threaded Verification*: In-process multi-threaded server testing and thread-safe routing without data races.
  4. *Multi-Process Cluster Simulation & Failure Resilience*: Real multi-process cluster tests executing over TCP loopback sockets, validating primary termination with replica fallback, dead primary write rejection under static topology, node restart with auto-reconnection, and timeout handling.
- **Alternatives Considered**:
  - *End-to-End Blackbox Testing Only*: Validates system as a whole, but makes identifying concurrency bugs and memory leaks significantly harder.
  - *Unit Tests Only*: Fails to catch distributed timing issues, race conditions, and network framing anomalies.
- **Trade-offs**:
  - Multi-process integration tests require managing OS child processes and ephemeral ports, but guarantee true end-to-end network fidelity.
- **Validation**:
  - Validated in `tests/test_failure_resilience.cpp` and `tests/test_network_integration.cpp`: clean replica fallback upon primary kill, write degradation on unreachable primary, automatic client reconnection on node restart, and bounded timeouts.

## ADR-009: Benchmarking Harness & Performance Analysis Methodology

- **Status**: Accepted
- **Context**: Evaluating distributed cache throughput, latency distribution, and scalability under varying concurrency levels, node counts, replication factors, and workload mixes requires an accurate, low-overhead load generator.
- **Decision**: Provide a standalone benchmark executable (`ringcache_bench`) and Python automation runner (`scripts/run_benchmarks.py`):
  - **Client Concurrency**: Each concurrent client worker thread instantiates its own `NetworkClusterRouter` with dedicated TCP sockets, avoiding client-side socket lock serialization and fully stressing the multi-threaded server worker pool.
  - **Monotonic High-Precision Timing**: All durations are measured using `std::chrono::steady_clock`. Latencies are recorded in thread-local vectors in microseconds ($\mu\text{s}$), eliminating lock contention during measurement.
  - **Percentile Calculation**: Latency distributions are sorted post-run and evaluated using the 0-indexed nearest-rank method: $\text{rank}(P) = \lfloor \frac{P}{100} \times (N - 1) \rfloor$ for $p50$, $p95$, and $p99$.
  - **Warm-Up Phase**: Configurable key pre-population (`--warmup`) ensures read operations measure actual cache hits rather than empty-cache misses.
  - **Machine-Readable Logging**: Performance metrics and experiment parameters are written to CSV format (`--out`).
- **Alternatives Considered**:
  - *External Generic Tools (memtier / redis-benchmark)*: Would require implementing full Redis/Memcached protocol compatibility.
  - *Shared Single-Router Client*: Contends on a single client-side socket lock per node, measuring client mutex bottleneck rather than server throughput.
- **Trade-offs**:
  - In-repo standalone tool provides exact protocol compatibility and zero external dependencies, but requires maintaining the benchmark CLI.
- **Validation**:
  - Validated with live multi-process cluster experiments across concurrency scaling ($C=1..8$), replication cost ($R=1$ vs $R=2$), and workload ratios, logged in `benchmark_results.csv`.
