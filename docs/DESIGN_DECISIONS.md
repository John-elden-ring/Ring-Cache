# RingCache Architecture & Design Decisions

This document records the architectural decisions, trade-offs, alternatives considered, and unresolved questions for RingCache. All decisions are marked as **Proposed** until validated through prototypes, benchmarks, or maintainer approval.

---

## Decision Status Legend
- **Proposed**: Under evaluation; rationale documented, but awaiting validation or implementation.
- **Accepted**: Approved by project maintainers and targeted for implementation.
- **Superseded**: Replaced by a subsequent architectural decision.

---

## ADR-001: Consistent Hashing vs. Modulo Hashing

- **Status**: Proposed
- **Context**: In a distributed cache, incoming keys must be mapped efficiently to a set of $N$ storage nodes. Under traditional modulo hashing ($\text{node} = \text{hash}(\text{key}) \pmod N$), changing cluster size from $N$ to $N \pm 1$ invalidates approximately $\frac{N}{N+1}$ of all keys. In large caches, this causes massive cache misses, cascading load to backend databases, and high network congestion.
- **Proposed Decision**: Implement a consistent hash ring where keys and node identifiers map onto an identical circular token space ($[0, 2^{64}-1]$ or $[0, 2^{32}-1]$ using a non-cryptographic hash function such as MurmurHash3 or xxHash). Keys route to the first node with a token $\ge \text{hash}(\text{key})$ (wrapping to the lowest token at ring boundary).
- **Alternatives Considered**:
  - *Modulo Hashing*: $O(1)$ routing calculation with zero memory overhead, but catastrophic invalidation upon node changes.
  - *Rendezvous (Highest Random Weight) Hashing*: Offers excellent redistribution properties, but key lookup requires evaluating $O(N)$ hash weights across all nodes, whereas consistent hashing can lookup in $O(\log V)$ via binary search.
  - *Range-based Partitioning*: Keys partitioned by lexicographical ranges; leads to hot spots under sequential key write workloads.
- **Trade-offs**:
  - Consistent hashing requires maintaining an ordered data structure (e.g., `std::map` or sorted `std::vector`) with $O(\log V)$ lookup time rather than $O(1)$ modulo arithmetic.
  - Non-uniform token distribution can cause uneven load unless mitigated by virtual nodes.
- **Unresolved Questions**:
  - Should key routing be evaluated client-side (smart client), by an intermediary proxy coordinator, or handled via node-to-node request forwarding?
  - Which 64-bit hash algorithm provides the best speed and bit distribution uniformity across arbitrary string keys?

## ADR-002: Virtual Nodes (vnodes) for Uniform Partitioning

- **Status**: Proposed
- **Context**: With standard consistent hashing, placing a single token per physical node frequently produces unequal partition sizes on the ring, leading to severe memory imbalances and traffic hot spots.
- **Proposed Decision**: Introduce virtual nodes (vnodes). Each physical node is assigned $V$ distinct virtual tokens (e.g., $V = 100\text{–}256$), generated by hashing the node identifier with an index suffix (e.g., `"node1#0"`, `"node1#1"`).
- **Alternatives Considered**:
  - *Single token per physical node*: Minimal memory footprint, but unacceptable variance in key allocation across small to medium clusters.
  - *Bounded-load consistent hashing*: Enforces strict load limits per node; adds dynamic coordination overhead.
  - *Capacity-weighted allocation*: Assign variable token counts proportional to machine hardware capacity.
- **Trade-offs**:
  - Vnodes provide substantially better uniformity across physical nodes and enable smoother data redistribution during node join/leave events.
  - Increases ring memory consumption ($N \times V$ entries) and makes binary search on the ring slightly slower ($O(\log(N \times V))$).
- **Unresolved Questions**:
  - What is the optimal default value for $V$ that balances ring lookup latency against distribution variance?
  - How will heterogeneous nodes (nodes with different RAM limits) configure their respective vnode counts dynamically?

## ADR-003: Storage Engine and LRU Eviction Policy

- **Status**: Proposed
- **Context**: Each cache node requires an efficient in-memory storage engine that enforces a hard memory ceiling and discards entries when capacity is saturated.
- **Proposed Decision**: Implement an exact Least Recently Used (LRU) eviction engine using a hash table (`std::unordered_map`) mapping keys to iterators of a doubly-linked list (`std::list`) containing key-value pairs.
  - Read/Write: Moves the accessed entry to the head of the list ($O(1)$).
  - Eviction: Removes entries from the tail of the list ($O(1)$).
  - Memory Tracking: Track byte size of keys and values upon insert/update/erase to enforce memory limits rather than raw entry counts.
- **Alternatives Considered**:
  - *Sampled LRU (Redis approach)*: Randomly samples $K$ keys and evicts the oldest among them. Reduces memory overhead and lock contention on read paths, but provides approximate eviction.
  - *Clock / Second-Chance Eviction*: Uses a circular buffer with a reference bit.
  - *LFU (Least Frequently Used)*: Tracks frequency rather than recency; more complex to implement and susceptible to stale frequency accumulation.
- **Trade-offs**:
  - Exact LRU provides predictable, optimal recency eviction.
  - Maintaining node order requires mutating the doubly-linked list on *read* operations, necessitating exclusive write locking or fine-grained lock striping even for `GET` requests unless access order updates are buffered or batched.
- **Unresolved Questions**:
  - Should read-path list promotions be batched/coalesced or moved to lock-free ring buffers to avoid write locks on `GET`?
  - Will keys and values be stored in contiguous arenas/pools to mitigate heap fragmentation?

## ADR-004: TCP Protocol and Message Framing

- **Status**: Proposed
- **Context**: Nodes must communicate with clients and peer nodes reliably over the network. The wire protocol must be efficient, lightweight, and resilient to packet fragmentation.
- **Proposed Decision**: Implement a length-prefixed binary framing protocol over stream-oriented TCP:
  - Header: Fixed-size header containing a Magic Byte (1B), Message Type/Command (1B: `GET`, `SET`, `DEL`, `RESPONSE`), Flags (2B), Request ID (4B), and Payload Length (4B).
  - Payload: Command-specific arguments or serialized key/value data.
- **Alternatives Considered**:
  - *Text-based protocol (RESP / Redis-compatible)*: Easy to debug via Telnet/Netcat and compatible with existing Redis tools, but incurs text-parsing and tokenizing overhead.
  - *HTTP/REST*: Simple to integrate with web clients, but high header overhead and parsing latency for a high-performance in-memory cache.
  - *gRPC / Protocol Buffers*: Strongly typed and schema-driven, but introduces heavy external library dependencies.
- **Trade-offs**:
  - Length-prefixed binary framing minimizes parsing overhead, eliminates delimiter escaping, and allows pre-allocating read buffers.
  - Binary protocols are less convenient to inspect via standard command-line tools without dedicated CLI tooling.
- **Unresolved Questions**:
  - Should we support a lightweight ASCII/RESP compatibility fallback for debugging and benchmarking with tools like `memtier_benchmark` or `redis-benchmark`?
  - What maximum payload and frame size limits should be enforced to prevent denial-of-service allocations?

## ADR-005: Multi-Node Replication Strategy

- **Status**: Proposed
- **Context**: In-memory nodes may fail or restart. To prevent total data loss and maintain cache availability, keys can be replicated across multiple nodes on the ring.
- **Proposed Decision**: Support successor-node replication with a configurable replication factor $R$ (e.g., $R=2$ or $R=3$).
  - For a key, the primary node is the first node encountered on the ring; the replicas are the next $R-1$ distinct *physical* nodes following clockwise.
  - Writes are sent to the primary node and asynchronously or semi-synchronously propagated to replicas.
- **Alternatives Considered**:
  - *No Replication (Cache Only)*: Treat the cluster as an ephemeral cache where misses fall back to the underlying database. Maximizes write throughput and simplicity, but leaves backend databases vulnerable to stampedes on node loss.
  - *Quorum Consensus (Dynamo-style $W + R > N$)*: Tunable consistency, but introduces complex versioning (vector clocks) and read repair overhead.
  - *Raft / Paxos State Machine Replication*: Strong linearizability, but significantly limits write performance and adds substantial coordination overhead unsuitable for transient cache workloads.
- **Trade-offs**:
  - Successor replication provides fault tolerance against node dropouts with low coordination latency.
  - Asynchronous replication introduces a risk of transient stale reads or data loss during sudden primary node failure.
- **Unresolved Questions**:
  - Should replication be asynchronous (fire-and-forget for maximum throughput) or semi-synchronous (acknowledgement required from at least one replica)?
  - How should conflicting writes be reconciled if network partitions occur?

## ADR-006: Concurrency and Threading Architecture

- **Status**: Proposed
- **Context**: The cache server must scale across modern multi-core processors, handling thousands of concurrent client connections and high operations-per-second (OPS).
- **Proposed Decision**: Employ an asynchronous non-blocking event-driven network I/O model (worker thread pool or thread-per-core) coupled with a partitioned/sharded cache storage engine:
  - Storage is split into $S$ independent hash buckets/stripes (e.g., $S = 64\text{–}256$), each protected by its own reader-writer lock (`std::shared_mutex`).
  - Read/write operations hash the key to determine the specific stripe, drastically reducing lock contention across concurrent worker threads.
- **Alternatives Considered**:
  - *Single-Threaded Event Loop (Redis model)*: Zero lock contention and simple implementation, but leaves multi-core CPUs underutilized without deploying multiple instances per host.
  - *Single Global Mutex*: Simple to implement initially, but quickly becomes a performance bottleneck under multi-threaded network I/O.
  - *Completely Lock-Free Hash Map*: Complex to implement correctly in C++17 with dynamic resizing and LRU list updates without memory reclamation hazards.
- **Trade-offs**:
  - Lock striping achieves high concurrency and throughput across multiple threads while keeping implementation complexity manageable.
  - Cross-stripe operations (e.g., global size calculation, bulk flush) require acquiring multiple stripe locks in a strict deterministic order to prevent deadlocks.
- **Unresolved Questions**:
  - What networking abstraction should be used? (Native platform sockets with non-blocking I/O vs. an established cross-platform library like Asio).
  - How will memory limits be enforced globally across independently striped LRU segments?

## ADR-007: Node Failure Detection and Ring Membership

- **Status**: Proposed
- **Context**: Nodes in a distributed cluster can crash, restart, or experience network partitions. The cluster must detect changes and update the hash ring accordingly.
- **Proposed Decision**: Adopt a two-phase evolutionary approach:
  - *Phase 1 (Initial)*: Static or coordinator-assisted configuration where cluster membership is defined via static configuration or a centralized health probe.
  - *Phase 2 (Target)*: Decentralized heartbeat / failure detector (e.g., phi-accrual or SWIM gossip protocol) to broadcast node join/leave/fail events and recompute the local ring.
- **Alternatives Considered**:
  - *Fully Centralized Coordinator (ZooKeeper / etcd / Consul)*: Simplifies consensus and membership, but introduces a heavy operational dependency.
  - *Static Configuration Only*: Simplest to test, but cannot handle dynamic cloud environments or automated failover.
- **Trade-offs**:
  - Phase 1 allows focusing first on storage and hashing correctness without building complex distributed consensus.
  - Phase 2 eliminates single points of failure but requires robust handling of split-brain scenarios and flap damping.
- **Unresolved Questions**:
  - During node departure, how are keys migrated from remaining replicas to newly assigned successors?
  - What heartbeat interval and timeout thresholds should trigger marking a node as temporarily degraded vs. dead?

## ADR-008: Testing Strategy and Fault Simulation

- **Status**: Proposed
- **Context**: Distributed caching systems suffer from subtle failure modes, including race conditions, data races, unbalanced key distributions, and partition edge cases.
- **Proposed Decision**: Implement a three-tiered testing methodology:
  1. *Unit Testing*: Test isolated components (LRU list, hash ring token placement, binary frame decoder, memory counters) using modern unit tests.
  2. *Distribution & Statistical Verification*: Dedicated tests measuring key distribution uniformity, variance, and redistribution percentages across simulated node additions and removals.
  3. *Concurrency & Sanitizer Suite*: Stress tests running concurrent readers and writers under AddressSanitizer (ASan), ThreadSanitizer (TSan), and UndefinedBehaviorSanitizer (UBSan).
  4. *Integration / Cluster Simulation*: Multi-node in-process or containerized tests simulating packet delays, dropped connections, and abrupt node terminations.
- **Alternatives Considered**:
  - *End-to-End Blackbox Testing Only*: Validates system as a whole, but makes identifying concurrency bugs and memory leaks significantly harder.
  - *Unit Tests Only*: Fails to catch distributed timing issues, race conditions, and network framing anomalies.
- **Trade-offs**:
  - Thorough testing infrastructure requires upfront investment in mockable network abstractions and deterministic time/scheduling controls.
  - Guarantees high stability, correctness, and confidence prior to production deployment.
- **Unresolved Questions**:
  - Which testing framework should be adopted for unit tests (GoogleTest vs. Catch2 vs. doctest)?
  - How will cluster integration tests be automated in CI without introducing slow running times?
